BLS API in Python: working examples for the public v2 endpoint

The Bureau of Labor Statistics side of the public data APIs list · the rent index here feeds the CPI rent vs HUD FMR comparison · every status code, message, and output on this page comes from live calls on 2026-09-07.

Five lines of Python, no key

The BLS public data API v2 serves federal statistics with no account and no key. One GET returns the latest unemployment rate:

import requests

r = requests.get(
    "https://api.bls.gov/publicAPI/v2/timeseries/data/LNS14000000",
    timeout=30,
)
r.raise_for_status()
series = r.json()["Results"]["series"][0]
latest = series["data"][0]
print(series["seriesID"])           # LNS14000000
print(latest["periodName"])         # August
print(latest["year"])               # 2026
print(latest["value"])              # 4.1

That ran on 2026-09-07 against the real endpoint, output verbatim. LNS14000000 is the seasonally adjusted unemployment rate, and 4.1 percent is the August 2026 print. The sections below cover the endpoint path, the series IDs worth calling, GET versus POST, and the limits that bite without a key.

The right URL path, learned the hard way

Two similar paths float around, and one of them dead-ends. The working base is:

https://api.bls.gov/publicAPI/v2/timeseries/data/

The other spelling, api.bls.gov/public/v2/... without the "API", redirects to the marketing site and then refuses bots:

curl -s -o /dev/null -w "%{http_code} %{redirect_url}\n" \
  "https://api.bls.gov/public/v2/timeseries/data/LNS14000000"
# 301 https://www.bls.gov/public/v2/timeseries/data/LNS14000000

Following that redirect lands on an Access Denied page with HTTP 403 and a note about bot activity. If your script gets a 403 from BLS, check the path before anything else: /publicAPI/v2/ works, /public/v2/ does not.

GET for one series, POST for several

The GET form puts the series ID in the path. It returns the latest observations, and that is all most quick checks need:

curl -s "https://api.bls.gov/publicAPI/v2/timeseries/data/LNS14000000"
# {"status":"REQUEST_SUCCEEDED","responseTime":88,"message":[],
#  "Results":{"series":[{"seriesID":"LNS14000000","data":[
#    {"year":"2026","period":"M08","periodName":"August",
#     "latest":"true","value":"4.1","footnotes":[{}]},
#    {"year":"2026","period":"M07","periodName":"July","value":"4.1"},
#    {"year":"2026","period":"M06","periodName":"June","value":"4.2"},
#    ...]}}

The same JSON came back through requests.get in the first example. Note the latest flag on the newest observation and that value arrives as a string; cast it to float before doing math.

For multiple series, year ranges, or catalogs, switch to POST with a JSON body. One call can carry several series IDs:

import requests

r = requests.post(
    "https://api.bls.gov/publicAPI/v2/timeseries/data/",
    json={
        "seriesid": ["CUSR0000SEHA", "LNS14000000"],
        "startyear": "2024",
        "endyear": "2026",
    },
    timeout=30,
)
r.raise_for_status()
payload = r.json()
assert payload["status"] == "REQUEST_SUCCEEDED", payload["message"]
for series in payload["Results"]["series"]:
    latest = series["data"][0]
    print(series["seriesID"], latest["periodName"], latest["year"], latest["value"])

Output verbatim from the live run on 2026-09-07:

CUSR0000SEHA July 2026 448.542
LNS14000000 August 2026 4.1

Both series came back in one response, each under its own seriesID key, newest observation first. One POST spent one query of the daily budget instead of two, which matters at 25 per day.

The keyless limit: 25 queries a day, counted server-side

BLS documents 25 queries per day without a registration key (500 per day with the free key from data.bls.gov). We tested the behavior by hammering the endpoint until it stopped answering: the first 16 calls in a burst returned REQUEST_SUCCEEDED, and every call after that returned HTTP 200 with a different body:

{
 "status": "REQUEST_NOT_PROCESSED",
 "responseTime": 0,
 "message": [
  "Request could not be serviced, as the daily threshold for total number of requests allocated to the user with registration key  has been reached."
 ],
 "Results": {}
}

Three things in that body matter for your code. The response is still HTTP 200, so raise_for_status() will not save you. The Results key holds an empty object, so indexing into it raises KeyError. And the real signal sits in status, which you have to check yourself:

import requests

def bls_latest(series_id):
    r = requests.get(
        f"https://api.bls.gov/publicAPI/v2/timeseries/data/{series_id}",
        timeout=30,
    )
    payload = r.json()
    if payload["status"] != "REQUEST_SUCCEEDED":
        raise RuntimeError(
            payload["status"] + ": " + "; ".join(payload["message"])
        )
    return payload["Results"]["series"][0]["data"][0]

Called after the counter ran out, that function raised RuntimeError: REQUEST_NOT_PROCESSED: Request could not be serviced, as the daily threshold..., which is the behavior you want instead of a silent empty result. Cache what you pull: the unemployment rate publishes monthly, so a script that runs hourly spends 720 queries a month on 12 distinct values.

The year window is generous without a key: a POST asking for 2023 through 2026 returned every month (44 observations), and a 10-year request came back intact with the message Year range has been reduced to the system-allowed limit of 10 years. BLS documents the per-request series cap at 25 for the keyless tier, and batching several IDs into one POST is the way to stretch the 25-a-day budget.

Why the rent CPI lags the market by 9 to 12 months

CUSR0000SEHA moves slowly by design, and scripts that treat it as a live rent feed get burned. BLS prices each sampled housing unit once every six months, most tenants are mid-lease when the survey reaches them, and renewals carry prior rent forward. The index at any release date blends leases signed across the past year or more, so a shift in asking rents takes roughly four quarters to work through to the printed number. That is the commonly cited 9-to-12-month lag, and it is why the index kept climbing while asking rents flattened in 2023.

Practical takeaway for code: use CUSR0000SEHA for smooth, consistent, month-over-month percent changes, and use asking-rent sources or HUD's FMR for current dollar levels. The full comparison of what each number measures lives in the CPI rent vs HUD FMR guide.

When a pinned dataset beats the API

Inside the keyless limits the API covers most one-off needs. It stops fitting when you need long history joined against other columns, repeatable runs that cannot spend the daily budget, or rows you can hand to someone else. That is the case for a pinned snapshot with a fixed schema, judged the way we describe in what is a CSV sample: check the columns, encoding, and row count before you commit to the full file. For the rent side specifically, our FMR dataset download gives you 51,895 ZIP-level rows as CSV, no daily counter involved.

FAQ

Is the BLS API free to use?

Yes. The public data API v2 at api.bls.gov answers without any key or account, and every example on this page ran with a plain requests call. The keyless tier allows 25 queries per day; a free registration key from data.bls.gov raises the daily volume and unlocks longer request bodies.

How many requests can I make to the BLS API without a key?

25 queries per day. The responses carry no rate-limit headers, and when the counter runs out the API still returns HTTP 200 with status REQUEST_NOT_PROCESSED and the message Request could not be serviced, as the daily threshold for total number of requests allocated to the user with registration key has been reached. Every call counts, including the single-series GET form, so batch series into one POST when you need several.

How do I pull unemployment or rent CPI from the BLS API in Python?

Send the series ID to https://api.bls.gov/publicAPI/v2/timeseries/data/ with requests: LNS14000000 for the unemployment rate and CUSR0000SEHA for the CPI rent of primary residence index. The first example on this page returns the latest unemployment observation (4.1 for August 2026) in five lines of Python, and the POST example shows how to batch both series in one call.
