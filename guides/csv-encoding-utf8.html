CSV encoding and UTF-8: the traps, with real files

Published 2026-09-10. Every output block on this page is what the command actually printed on 2026-09-10 against sample files you can download from this site.

Encoding breaks CSV imports in two directions. A UTF-8 file read with the wrong assumption shows mojibake or a UnicodeDecodeError; a file saved by Windows tools carries a BOM that renames your first column or Windows-1252 endings that glue a carriage return to your last field. This page runs all four traps against real CSVs published on this site, shows what each error looks like verbatim, and gives the fix in pandas, the Python standard library, and jq.

What encoding means for a CSV

A CSV file is bytes on disk. Encoding is the table that maps those bytes to characters. ASCII covers 127 characters and fits in one byte each, which is why an all-ASCII CSV works everywhere. UTF-8 keeps ASCII byte-for-byte identical and extends it with multi-byte sequences, so one file can hold English, Japanese, currency symbols, and emoji. Windows-1252 is a single-byte codepage for Western European languages that cannot represent anything outside its 256 characters.

The practical rule: publish and read UTF-8, expect the two Excel quirks (BOM and Windows-1252 exports), and check line endings once. Our own files sit exactly on this fault line, which is why the examples below are not invented.

Trap one: emoji force UTF-8

Four of the five sample CSVs on this site are plain ASCII. The fifth, the Superteam Earn bounty listings sample, cannot be: bounty titles arrive with emoji in them. One row of the real file:

e92e317b-0d0f-49f4-9937-0623d4816df6,zns-sol,🟢 ZNS Solana Creator Challenge,bounty,500,USDC,,,2026-09-09,OPEN,AGENT_ALLOWED,0,ZNS Connect,11,17

The green circle is four bytes in UTF-8 (f0 9f 9f a2). That single cell decides the whole file's encoding: save it as Windows-1252 and the character does not exist. Saving from Python shows the failure verbatim:

UnicodeEncodeError: 'charmap' codec can't encode character '\U0001f7e2' in position 6: character maps to 
encoding with 'cp1252' codec failed

This is the direction where data is truly destroyed. Excel and older tools respond to that same condition differently, by substituting ? or dropping the character, and the original is gone. If your data holds names in any script beyond Western European, a single-byte encoding will eat them the same way.

Trap two: the Excel BOM renames your first column

Excel's "CSV UTF-8" save option writes a byte order mark, three bytes (ef bb bf) before the header row. The BOM tells Excel itself "this file is UTF-8", but most Python code does not expect it, and it lands on the first column name. Reproduced against a copy of the HUD FMR sample with the BOM prepended:

import csv
with open("boms.csv", newline="", encoding="utf-8") as f:
    rows = list(csv.DictReader(f))
rows[0]["zip"]
Traceback (most recent call last):
  File "<stdin>", line 4, in <module>
KeyError: 'zip'

The column exists. Its name starts with an invisible character, which is why the lookup fails and why this trap survives most debugging sessions. Printing the real key:

'\ufeffzip'

The fix is one string: utf-8-sig means "UTF-8, and strip a BOM if one is present", and it reads plain UTF-8 without a BOM just fine, so it is a safe default for any file an Excel user might have touched.

with open("boms.csv", newline="", encoding="utf-8-sig") as f:
    rows = list(csv.DictReader(f))
print(rows[0]["zip"], rows[0]["metro"])
76437 metro

jq is immune here: it strips the BOM from input automatically. Python's json module refuses files with a BOM, so the same three bytes behave differently one file format over.

Trap three: Windows-1252 turns UTF-8 into mojibake

The reverse read is quieter: no error, just wrong text. Decode the UTF-8 bounty sample as Windows-1252 and the green circle becomes three Latin characters:

ðŸŸ¢ ZNS Solana Creator Challenge

Four UTF-8 bytes, four single-byte characters. Nothing raised an exception, so a script that only checks for errors now stores garbage in a database and nobody notices for weeks. That asymmetry is worth internalizing: wrong decoding of a UTF-8 file usually fails silently, while wrong decoding of a Windows-1252 file as UTF-8 fails loudly with UnicodeDecodeError on the first high byte.

The fix for existing mojibake is the same reopen, not a find-and-replace over the broken text: re-encoding the garbled string back through cp1252 to bytes, then decoding as UTF-8, recovers 🟢. The fix for imports is knowing the encoding before you read, which is the next section.

Trap four: CRLF line endings glue \r to your last field

Windows tools end lines with two bytes, carriage return plus line feed, and Unix tools expect one. Our scraper pack manifest sample ships with CRLF endings, honestly detectable in the file listing:

file data/scraper-pack/sample.csv data/earn-bounties/sample.csv
data/scraper-pack/sample.csv:   ASCII text, with CRLF line terminators
data/earn-bounties/sample.csv:  CSV Unicode text, UTF-8 text

csv and pandas handle CRLF when the file is opened with newline="". Hand-rolled split("\n") parsers do not. Same file, both ways:

text = open("data/scraper-pack/sample.csv").read()
last = text.split("\n")[2].split(",")
print(repr(last[-1]))
' saves JSON"'
with open("data/scraper-pack/sample.csv", newline="") as f:
    rows = list(csv.reader(f))
print(repr(rows[2][-1]))
'Scrolls a feed to the end, dedupes, saves JSON'

The hand-rolled version kept the closing quote and the trailing \r, so the field compares unequal to Scrolls a feed to the end, dedupes, saves JSON, and any join or dedup on that column misses. Splitting on commas also breaks here because the field contains a quoted comma; that is CSV to JSON in Python territory.

How to detect a CSV's encoding, and why one detector lies

The file command inspects actual bytes and gets it right:

file --mime data/earn-bounties/sample.csv
data/earn-bounties/sample.csv: text/csv; charset=utf-8

Statistical guessers do worse on small files. chardet, the library people reach for first, examined the same 1.9 KB emoji file and reported:

data/earn-bounties/sample.csv: Windows-1252 with confidence 0.6792384105960264

That guess is wrong, and at 68 percent confidence. UTF-8 emoji bytes look like high Windows-1252 characters to any frequency-based detector without enough data. On a 50 MB file chardet would nail it; on a 20-row sample it will steer you wrong. Its maintained successor charset_normalizer guesses more reliably, but for small files the honest order is: documentation first, file --mime second, raw bytes third:

head -c 20 data/earn-bounties/sample.csv | xxd
00000000: 6964 2c73 6c75 672c 7469 746c 652c 7479  id,slug,title,ty
00000010: 7065 2c72                                pe,r

No ef bb bf at the start, so no BOM; ASCII header, so the interesting bytes sit deeper in the file. Detection settles the question in three commands, which is cheaper than a botched import every time.

Fixes in pandas and the jq gotcha

pandas takes the same codec names as the standard library in read_csv. The two worth memorizing:

import pandas as pd

df = pd.read_csv("boms.csv", encoding="utf-8-sig")   # strips the Excel BOM if present
df = pd.read_csv("win1252.csv", encoding="cp1252")   # Windows-exported files

encoding="latin-1" is the never-fails escape hatch: it maps all 256 byte values, so it always opens the file, though characters outside its table come out as neighbors. For messy imports where a few bad rows are acceptable, pandas also takes encoding_errors="replace" and continues with U+FFFD markers in place of undecodable bytes. All of this assumes you identified the encoding first; latin-1 on a UTF-8 file is mojibake by construction. Encoding is one read-time parameter among several; the full parameter tour, dtype, usecols, parse_dates, na_values, chunksize, sep, and header, with the same verbatim-output format, is in Python read CSV: a pandas read_csv tutorial.

jq rarely trips on encoding itself: it reads UTF-8 natively, strips a BOM, and writes emoji back untouched. The jq gotcha on this site is structural instead. Our JSON files use an envelope, {slug, name, columns[], records[]}, and the obvious first query fails:

jq -r '.[0].title' data/earn-bounties/sample.json
jq: error (at .../data/earn-bounties/sample.json:193): Cannot index object with number
jq -r '.records[0].title' data/earn-bounties/sample.json
🟢 ZNS Solana Creator Challenge

Same emoji round-trips through jq -r and hexdump shows the original four bytes, f0 9f 9f a2, which is the end-to-end proof that the file was UTF-8 all along.

CSV encoding FAQ

What encoding should a CSV file use?

UTF-8. It represents every language, currency sign, and emoji, Python 3, pandas, jq, and modern databases default to it, and it needs no BOM. The one exception is feeding a CSV back into older Excel on Windows, which expects the Windows-1252 codepage or a UTF-8 file with a BOM; save as "CSV UTF-8" and keep the BOM in that case.

Why does my CSV show weird characters like ðŸŸ¢ instead of an emoji?

The file is UTF-8 but the program reading it assumed Windows-1252, so each byte of the multi-byte emoji becomes a separate Latin character. This mojibake is a decode mismatch, not corruption: reopening the file with the correct encoding (utf-8, or utf-8-sig if it starts with an Excel BOM) restores the original characters. The reverse mismatch, saving UTF-8 text as Windows-1252, really does destroy data when the characters are outside the codepage.

How do I fix a UnicodeDecodeError when reading a CSV in pandas?

Identify the real encoding first with file --mime or by reading the first bytes, then pass it to read_csv as encoding="cp1252" (Windows exports), "utf-8-sig" (strips the Excel BOM if present, works on plain UTF-8 too), or "latin-1", which always succeeds because it maps all 256 byte values. pandas also accepts encoding_errors="replace" for imports where a few bad rows are acceptable.
