CSV vs Excel: which format for your data?

Published 2026-09-10. Every error string and row count on this page comes from the FMR dataset download build and the free sample files on this site, checked 2026-09-10. Data Vault is not affiliated with HUD.

The short answer

Ship a CSV when the file is one flat table that code will read: one row per record, one header line, text all the way down. Ship an XLSX when the workbook is the product: several sheets, formulas that recompute, formatting a human reviews. The two formats fail in different ways, and the amount of machinery between your data and the reader decides which failure modes you inherit.

One government release demonstrates both sides. HUD publishes FY2026 fair market rents as two Excel workbooks that resist parsers in three separate layers, and the same numbers exist on this site as a 51,895-row CSV that loads in one pd.read_csv call. That case study sits in the middle of this page, followed by a per-scenario decision matrix and the round-trip trap that catches people who move between the two formats casually.

What each format actually is

A CSV file is plain text: header row, comma-separated values, one record per line, UTF-8 or another single encoding. That is the whole spec, which is why pandas, R, jq, every database loader, every spreadsheet, and every version-control system read it without a library decision. The trade is symmetry: no formulas, no types, no sheets, no formatting. What is on disk is what everyone sees, byte for byte, which is also why git diff on a CSV produces a readable review and git diff on an XLSX produces a binary shrug.

An XLSX file is a zip archive of XML parts: the sheet data, a shared-strings table, styles, and document properties. Excel assembles and renders all of it, which is where its powers come from: formulas stored as definitions rather than results, values recalculated on open, multiple sheets in one file, freeze panes and number formats that survive round trips between Excel users. The trade is the machinery. More layers mean more places to refuse to open, and a file that needs Excel, openpyxl, or another spreadsheet library to touch at all. The next section shows what one malformed property file does to that stack.

Case study: HUD's two workbooks versus our one CSV

We built the HUD Fair Market Rents FY2026 pack by parsing HUD's two official workbooks with openpyxl. The parse works now. The first pass hit three problems, one per XLSX layer, and each is documented with verbatim strings in the FMR dataset download guide:

The document properties refused to load. The county workbook FY26_FMRs_revised.xlsx ships with a malformed timestamp in its document properties, 2026- 2-19T18:17:31Z, a space where the month padding should be. openpyxl dies with Unable to read workbook: could not read properties before a single row is visible. The fix ran below the file format entirely: unzip the xlsx, patch the two property files with a regex, rezip. A spreadsheet's own metadata blocked every tool that reads spreadsheets, and no CSV has metadata to corrupt.

The header row carried line breaks. The SAFMR workbook's first column is named ZIP\nCode and the rent columns read like SAFMR\n0BR -\n90%\nPayment\nStan..., raw newline characters inside header cells. Any join by column name has to strip those first. The same header in CSV would be a comma-separated line of text you can read with head -1, and a broken one would be visible in any text editor.

The cells stored display strings. Rent values came out as whatever the spreadsheet last displayed: strings like '850', floats like 1090.0, comma-formatted text in the county file. Eighteen columns carried six usable values (the FMR plus 90% and 110% payment-standard variants for five bedroom sizes), so the parser walked the row with a stride of three. Our cleaned CSV, fmr-by-zip-2026.csv, does none of this: 51,895 rows, ten columns, bare integers, zero empty rent cells, plain UTF-8, only area_name quoted because metro names contain commas. One dtype hint (zip as text, for the 3,533 leading-zero rows) and the file is a dataframe.

None of this is criticism of HUD. The workbooks are built for program staff reading tables, and in that job they are fine. As a container for data that code consumes, the XLSX layer added three failure modes the CSV never has, and the FMR dataset download guide shows the exact parsing session against both.

Decision matrix: which format per scenario

ScenarioPickWhy
Loaded by pandas, R, SQL, or a query toolCSVOne header, no formulas, no zip layer; the HUD file loads in one line with one dtype hint
Version control in gitCSVText diffs and reviewable pull requests; an XLSX diff is binary noise
Same data going to many tools and peopleCSVEvery language, BI tool, and spreadsheet reads text; nothing to install

Formulas that must recomputeXLSXExcel stores formula definitions, not just results; CSV stores nothing but text
Several tables in one file (per-metro tabs, a README sheet)XLSXCSV is one table per file; multi-table means several CSVs or one workbook

Two scenarios sit together at the bottom and cause most of the damage in practice: a workbook that grew into the system of record, then a CSV export that has to survive the trip into code. The export direction is safe. The reverse is where formats eat data.

The round-trip trap: what Excel does to a CSV on open and save

Opening a CSV in Excel, touching a cell, and saving it back runs the file through Excel's type inference twice, and the save writes Excel's decisions, not yours. Three manglings, all against real columns from files on this site:

Leading zeros die. Excel reads 00601 as the number 601. In our HUD file, 3,533 of 51,895 rows have a ZIP starting with zero (3,004 unique ZIPs, the 006xx Puerto Rico range and the 0xxxx New England range among them), and one open-save cycle breaks every join against a geography table keyed on five characters. The HUD FMR Excel guide shows the import settings that keep the column text in the first place.

Dates get reinterpreted. A text cell holding 2026-09-09, the format every date in our bounty listings sample uses, becomes a real date cell on open, and the save writes it back in the locale's display format: 09/09/2026 on a US machine, something else on an EU one. Values that merely look like dates or fractions get converted too. A pandas import expecting ISO strings then fails or, worse, silently mixes formats across rows.

Encoding shifts underneath you. Excel's "CSV UTF-8" save option writes a byte order mark, ef bb bf, ahead of the header, and Python code that looked up the column zip starts failing with KeyError: 'zip' because the real key is \ufeffzip. Save from a Windows locale without the UTF-8 option and the file comes back Windows-1252, where characters outside the codepage are destroyed: the green circle emoji in our bounty sample, four bytes (f0 9f 9f a2) in UTF-8, has no Windows-1252 form. The CSV encoding and UTF-8 guide reproduces both failures verbatim with the fixes.

One more, briefly: a 19-digit ID like the Airbnb listing IDs in our sample exceeds what numeric columns hold exactly (past 2 to the 53rd power), so it comes back rounded and re-rendered in scientific notation. That trap and the Tableau version of it are in the Airbnb data in Tableau guide.

The working pattern costs nothing: keep the XLSX as the human-facing working file, export a CSV when code needs data, and never save the CSV back over itself from Excel. On the code side, pin the types on import (pd.read_csv(..., dtype={"zip": str})) and check whether a free CSV sample survives the import before writing loader code against the full file.

CSV vs Excel questions

Is CSV or Excel (XLSX) better for data analysis?
For analysis that code will run (pandas, R, SQL, or a query tool), CSV: one flat table, no formulas to break, loadable in one line like pd.read_csv. Excel wins when the workbook itself is the deliverable: formulas that recompute, several sheets, formatting a reviewer reads. HUD's FY2026 rent release ships both ways: two official XLSX workbooks that fight parsers, and the same numbers cleaned into a 51,895-row CSV that loads with zero type fixes beyond reading ZIP codes as text.
What does Excel change when it opens and saves a CSV?
Three things, all reproducible: ZIP codes lose leading zeros, so 00601 becomes 601 (3,533 rows in our 51,895-row HUD file start with zero); ISO dates like 2026-09-09 come back in the locale's display format on save; and the 'CSV UTF-8' save option writes a BOM that renames the first column in Python (the header zip becomes \ufeffzip). Long numeric IDs can return in scientific notation with trailing digits lost. None of this shows a warning dialog.
How do I convert an Excel workbook to CSV without losing data?
Excel exports only the active sheet, and formulas export as their last calculated values, not their definitions, so a multi-sheet workbook becomes one CSV per sheet. Expect the format itself to resist: HUD's county workbook FY26_FMRs_revised.xlsx ships a malformed timestamp in its document properties (2026- 2-19T18:17:31Z) that stops openpyxl with 'Unable to read workbook: could not read properties' before any row loads; the fix was unzipping the xlsx, patching the property files, and rezipping. Save the export as UTF-8, then verify the leading-zero and date columns survived before the file goes anywhere.
