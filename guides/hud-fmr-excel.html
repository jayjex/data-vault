HUD FMR in Excel: the official workbooks, clean imports, and formulas

FY2026 edition, published 2026-09-10. Data source: HUD, public domain. Data Vault is not affiliated with HUD. This page documents the data; it is not housing or legal advice.

Huduser.gov publishes the FY2026 Fair Market Rent data as two Excel workbooks: FY26_FMRs.xlsx (368 KB, 4,764 county-level rows) and fy2026_safmrs.xlsx (4.2 MB, 51,895 ZIP-level rows). Both open in Excel and Google Sheets. Both need a few settings handled before the data is usable: the SAFMR sheet's header cells contain line breaks, values are stored as mixed text and numbers, and a default import strips the leading zeros off 3,533 ZIP codes.

This guide walks the real structure of each workbook (checked against the files HUD serves today), the import settings that get a clean load in Excel and Google Sheets, and lookup formulas that run once the data is in. If your goal is repeated lookups rather than reading a spreadsheet once, the HUD FMR FY2026 pack ships the same values as one flat CSV; the FMR dataset download guide covers the pandas side.

The two official HUD FMR workbooks

Both files live on the HUD FMR datasets page under the FY2026 section:

FileSizeRowsWhat one row is
FY26_FMRs.xlsx368 KB4,764 data rows, 2 sheetsOne county (or county-equivalent) FMR area
fy2026_safmrs.xlsx4.2 MB51,895 data rows, 1 sheetOne ZIP code

The county workbook's first sheet, FY26_FMRs, carries 14 columns: stusps, state, hud_area_code, countyname, county_town_name, metro, hud_area_name, fips, pop2023, and one fmr column per bedroom size (fmr_0 through fmr_4). The second sheet, Field_Descriptions, documents those columns in 15 rows. First data row, read straight from the file: Autauga County, AL, hud_area_code METRO33860M33860, in the Montgomery, AL MSA, with fmr_0 = 860 and fmr_2 = 1016.

The ZIP workbook has a single sheet, SAFMRs, with 18 columns. Its Abilene, TX MSA row carries base FMRs of 850 / 880 / 1090 / 1420 / 1710 for 0BR through 4BR, the same numbers as ZIP 76437 in the free sample on this site. The two workbooks together are the full FY2026 publication; every value in our CSV pack traces back to them.

What the sheets actually look like

The SAFMR sheet's header row is the first surprise. The header cells contain hard line breaks, because HUD formats them to wrap inside narrow columns. Read programmatically, the first two and one value column come out like this:

Cell A1: 'ZIP\nCode'
Cell B1: 'HUD Area Code'
Cell J1: 'SAFMR\n2BR'
Cell K1: 'SAFMR\n2BR - 90%\nPayment\nStandard'
Cell L1: 'SAFMR\n2BR - 110%\nPayment\nStandard'

Each bedroom size gets three columns: the base SAFMR, then 90% and 110% payment standard variants. That makes 5 bedroom sizes x 3 columns = 15 value columns, plus ZIP Code, HUD Area Code, and Area Name = 18. If you parse the sheet in code, the base FMRs sit at every third column starting from the fourth; in Excel terms, columns D, G, J, M, P hold the base values and the columns between hold the 90% and 110% figures.

Value cells mix text and numbers in the same column. In the Abilene row, the 0BR and 1BR cells hold text strings ('850', '880') while the 2BR, 3BR, and 4BR cells hold real numbers (1090, 1420, 1710). The county workbook does the same, and pop2023 arrives as a number next to fips codes stored as text. Sorting or averaging a column with mixed types gives wrong results or #VALUE! errors, so the import step below forces consistent types.

The county workbook's headers are flat by comparison (no line breaks), but its first sheet also carries two nearly identical name columns, countyname and county_town_name, and the metro column is a 0/1 flag rather than a label.

Import into Excel cleanly

Double-clicking the xlsx opens it as-is, since it already is a workbook. The steps below matter when you convert the sheet into a typed table, or when you bring in a CSV export instead:

  1. Data > Get Data > From File > From Text/CSV (or From Workbook for the xlsx).
  2. In the preview, click Transform Data, not Load.
  3. Power Query: set every fmr / SAFMR column to Whole Number (Transform > Data Type). This kills the text-vs-number mix in one pass.
  4. Set the ZIP or fips column to Text before anything else touches it. This is the step that saves the leading zeros.
  5. Home > Close & Load. The data lands as a typed Excel table.

On the ZIP workbook you can also delete the 90% and 110% columns in the same Power Query session (right-click > Remove Other Columns, keeping D, G, J, M, P among the value columns), which leaves a 9-column base-FMR table.

Import into Google Sheets

Sheets cannot open a remote xlsx by URL, so download the workbook first, then File > Import > Upload. Two settings decide whether the load is clean:

  • Uncheck Convert text to numbers, dates, and formulas. Checked, it reads '850' as 850 (fine) but also reads ZIP 01960 as 1960 (bad). Unchecked, every column imports as text; select the FMR columns afterward and Format > Number > Number.
  • Separator: automatic works for both workbooks.

For a CSV instead of the workbook, IMPORTDATA pulls a file straight from a URL:

=IMPORTDATA("https://jayjex.github.io/data-vault/data/hud-fmr-2026/sample.csv")

IMPORTDATA applies the same number conversion, so the ZIP column loses leading zeros on the 0-prefixed rows. Wrap the fix around it, then VLOOKUP against the converted key:

=ARRAYFORMULA(TEXT(IMPORTDATA("...sample.csv"), "00000"))

applied to the ZIP column, or simply import through File > Import with conversion off.

The leading zero ZIP trap, counted

In the FY2026 ZIP-level data, 3,533 of the 51,895 ZIP rows start with 0: all of Puerto Rico (006xx), the New England states (01xxx through 04xxx), and scattered others. A default Excel or Sheets import treats those cells as numbers, drops the zero, and the ZIP becomes a 4-digit value. Everything downstream breaks quietly: VLOOKUPs against a 5-character key return #N/A for exactly those 3,533 rows, and joins by ZIP drop New England and Puerto Rico without any error message.

The fix is one setting at import time: read the ZIP column as Text (Power Query step above, wizard step 3, or Sheets conversion unchecked). If the damage is already done, =TEXT(A2,"00000") rebuilds the 5-character form from a numeric column, as long as no digits beyond the leading zero were lost.

The same trap applies to the county workbook's fips column and to any CSV you import later. The CSV pack sidesteps it: ZIPs ship quoted as text, and the FMR by ZIP guide shows the full lookup workflow against that file.

Formulas to run once the data is in

Examples use the free 22-row sample CSV, 10 columns, ZIP in column A, fmr_2br in column H, headers in row 1, data in rows 2 through 23. All three return values from the Abilene, TX MSA rows:

  • 2BR FMR for one ZIP: =VLOOKUP("79508", A:H, 8, FALSE) returns 1240.
  • Same lookup with a visible miss value: =XLOOKUP("79562", A2:A23, H2:H23, "ZIP not in file") returns 1900, the highest 2BR SAFMR in the sample. Note the lookup key is a text string, which matches the Text-typed ZIP column; if you pass the number 79562, Excel will not find it.
  • Average 2BR FMR across one metro in the sample: =AVERAGEIF(B2:B23, "METRO10180M10180", H2:H23) returns 1177 over the 22 sample ZIPs, all in that one metro.

On the full 51,895-row file the same formulas run unchanged with the ranges widened. Keep the lookup key and the ZIP column the same type (both text or both numbers) or the match fails silently on half the file.

When the workbook is fine, and when the CSV wins

Reading one county's numbers once? The official workbook is fine; open it, look, close it. The import friction only pays off once.

Building anything that repeats (a monthly rent-comps sheet, a payment-standard calculator, a lookup fed by a list of ZIPs), the flat CSV wins on three counts: one table instead of two workbooks with different layouts, one consistent type per column instead of mixed text and number cells, and a header row you can reference by name. HUD FMR Excel questions

Does HUD publish FMR data as an Excel file?
Yes. HUD's FY2026 release ships two Excel workbooks on huduser.gov: FY26_FMRs.xlsx with 4,764 county-level rows across 2 sheets, and fy2026_safmrs.xlsx with 51,895 ZIP-level rows on one sheet. Both are real .xlsx files that open in Excel, but their layout (newline-broken headers, values stored as mixed text and numbers) makes a clean import take a few extra steps.
Why do my ZIP codes lose their leading zeros in Excel?
Excel reads a ZIP like 01960 as the number 1960 and drops the zero. In the FY2026 ZIP-level data, 3,533 of 51,895 ZIP rows start with 0, so a default import silently corrupts them. Fix it by importing the zip column as Text: in Power Query, set the column type to Text before Close & Load; in the older Text Import Wizard, set that column to Text in step 3; in Google Sheets, uncheck Convert text to numbers during File > Import.
Is there a cleaner file than the official FMR workbooks?
Yes, if your work is lookups rather than one-off reading. The HUD FMR FY2026 CSV pack collapses both workbooks into one flat 10-column table (zip, hud_area_code, metro, area_name, state, fmr_0br through fmr_4br) with ZIPs kept as text. A free 22-row sample shows the exact schema, and VLOOKUP or XLOOKUP runs on it with no cleanup.
