Build an MCP server in 76 lines of Python

Published 2026-09-10. Code and outputs captured live on 2026-09-07 with Python 3.14.4 on Linux; the same server passed a handshake from the official TypeScript MCP SDK 1.30.0 the same day. Every output below is verbatim from those runs.

What you are building

An MCP (Model Context Protocol) server is a program that answers JSON-RPC 2.0 requests from an agent client. The stdio transport, the one Claude Desktop and most coding agents use, is the simplest case: the client starts your process, writes one JSON object per line to its stdin, and reads one JSON object per line from its stdout. No sockets, no auth, no framework.

A working server answers three requests: initialize (name and version), tools/list (what tools exist, with JSON Schema input descriptions), and tools/call (run one tool, return text content). This page builds one from the standard library alone so every moving part stays visible, then shows where the official SDK takes over.

The example server exposes two tools over a two-row notes dictionary: notes_search for keyword matching and notes_get for fetch-by-id. Toy data on purpose; the point is the protocol around it. Our production server dataset-mcp follows the same request loop at larger scale, and its design is the reference for the publishing section.

The whole server

76 lines including blank lines. Save as server.py:

#!/usr/bin/env python3
"""Minimal MCP server over stdio: notes_search / notes_get, JSON-RPC 2.0."""
import json
import sys

NOTES = {
    "n1": {"title": "Airport pickup", "body": "Terminal 3, 14:30, plate ends 8821"},
    "n2": {"title": "Fridge", "body": "Buy oat milk, limes, coffee beans"},
}

def handle(method, params, id_):
    if method == "initialize":
        result = {"protocolVersion": params.get("protocolVersion", "2025-06-18"),
                  "capabilities": {"tools": {}},
                  "serverInfo": {"name": "notes-mcp", "version": "0.1.0"}}
    elif method == "tools/list":
        result = {"tools": [
            {"name": "notes_search",
             "description": "Search notes by keyword; omit query to list all",
             "inputSchema": {"type": "object",
                             "properties": {"query": {"type": "string",
                                           "description": "Case-insensitive keyword"}},
                             "required": []}},
            {"name": "notes_get",
             "description": "Fetch one note by id",
             "inputSchema": {"type": "object",
                             "properties": {"id": {"type": "string"}},
                             "required": ["id"]}}]}
    elif method == "tools/call":
        name, args = params["name"], params.get("arguments", {})
        try:
            if name == "notes_search":
                q = args.get("query", "").lower()
                hits = [{"id": i, "title": n["title"]} for i, n in NOTES.items()
                        if not q or q in n["title"].lower() or q in n["body"].lower()]
                text = json.dumps({"matches": hits})
            elif name == "notes_get":
                try:
                    text = json.dumps(NOTES[args["id"]])
                except KeyError:
                    return {"jsonrpc": "2.0", "id": id_, "result": {"content": [
                            {"type": "text", "text": "unknown id: valid ids are n1, n2"}],
                            "isError": True}}
            else:
                return {"jsonrpc": "2.0", "id": id_, "result": {"content": [
                        {"type": "text", "text": f"unknown tool: {name}"}],
                        "isError": True}}
            return {"jsonrpc": "2.0", "id": id_, "result": {"content": [{"type": "text", "text": text}]}}
        except Exception as e:
            return {"jsonrpc": "2.0", "id": id_, "result": {"content": [
                    {"type": "text", "text": f"{type(e).__name__}: {e}"}], "isError": True}}
    else:
        return {"jsonrpc": "2.0", "id": id_, "error": {"code": -32601,
                "message": f"Method not found: {method}"}}
    return {"jsonrpc": "2.0", "id": id_, "result": result}

def main():
    for line in sys.stdin:
        line = line.strip()
        if not line:
            continue
        try:
            req = json.loads(line)
        except json.JSONDecodeError:
            sys.stdout.write(json.dumps({"jsonrpc": "2.0", "id": None, "error": {
                "code": -32700, "message": "Parse error: request was not valid JSON"}}) + "\n")
            sys.stdout.flush()
            continue
        if "method" not in req or req["method"].startswith("notifications/"):
            continue
        out = handle(req["method"], req.get("params", {}), req["id"])
        sys.stdout.write(json.dumps(out) + "\n")
        sys.stdout.flush()

if __name__ == "__main__":
    main()

The structure is worth reading once slowly. main() owns the transport: read a line, skip blanks and notifications (requests without an id expect no reply), parse, dispatch, write one line back, flush. handle() owns the three protocol methods, and everything under tools/call is ordinary code you already know how to write.

The three response shapes

Everything a tools-bearing server returns lands in one of three shapes, and the run above shows all three. Picking the right one is most of the error-handling design:

Plain result. Responses 1 through 3. The method ran, the answer rides in result. For tools/call the result carries a content array, and text content is the workhorse: our server JSON-encodes structured answers into that string. dataset-mcp does the same, so a query like query_dataset("hud-fmr-2026", {where: [{column: "state", op: "=", value: "TX"}], limit: 5}) arrives at the model as 5 rows of JSON text inside one content block.

Tool error (isError: true). Responses 4 and 5. The protocol worked, the tool call did not. Unknown tool names, bad arguments, a slug that matches nothing: answer with a normal result whose isError flag is true and whose text says what went wrong and what would work instead. The model reads that text and corrects course. Note response 4 lists the valid ids; an error message that names the valid inputs saves the next round trip. dataset-mcp follows the same rule for bad slugs and bad operators, replying with the valid values listed.

Protocol error (error object). Responses 6 and 7. The request itself broke the protocol: a method the server never declared (-32601), or a line that was never valid JSON (-32700). These are JSON-RPC errors with numeric codes, not tool results, because the client (or its SDK) handles them differently from a failed tool call.

Connect a real client

A hand-rolled tools/call proves the server answers its own protocol. A client built on the official SDK is the stronger test, because that is what Claude Desktop and the agents actually are. Twenty lines of TypeScript against @modelcontextprotocol/sdk 1.30.0:

import { Client } from "@modelcontextprotocol/sdk/client/index.js";
import { StdioClientTransport } from "@modelcontextprotocol/sdk/client/stdio.js";
const t = new StdioClientTransport({ command: "python3", args: ["server.py"] });
const c = new Client({ name: "verify-client", version: "0.0.1" });
await c.connect(t);
const tools = await c.listTools();
console.log("tools:", tools.tools.map(x => x.name).join(", "));
const hit = await c.callTool({ name: "notes_search", arguments: { query: "fridge" } });
console.log("search:", hit.content[0].text);
const miss = await c.callTool({ name: "notes_get", arguments: { id: "n9" } });
console.log("miss isError:", miss.isError, "| text:", miss.content[0].text);
await c.close();
console.log("SDK handshake OK");

Output, verbatim:

tools: notes_search, notes_get
search: {"matches": [{"id": "n2", "title": "Fridge"}]}
miss isError: true | text: unknown id: valid ids are n1, n2
SDK handshake OK

The SDK client drove the raw Python server with no changes on either side. That is the compatibility bar to clear, and clearing it with zero dependencies means the protocol floor is genuinely low. The SDK earns its keep one level up: schema validation for arguments, request batching, and the HTTP transports. A comparable server on the SDK side of the fence is roughly 40 lines of JavaScript importing McpServer and StdioServerTransport, which is exactly how dataset-mcp is built.

Publish it: GitHub repo to npx install

An MCP server nobody can install is a demo. The install path we use ships the repo on GitHub and lets clients run it straight from git: npx github:youruser/your-repo. dataset-mcp installs exactly this way, and its repo layout is the template:

dataset-mcp/
  index.js            # entry file at repo root, shebang on line 1
  package.json        # name, bin, files, engines
  package-lock.json
  README.md           # config JSON for Claude Desktop and TOML agents
  LICENSE             # MIT
  server.json         # MCP registry declaration
  data/               # manifest the server fetches at runtime

The package.json fields that matter (abbreviated from dataset-mcp v1.1.0):

{
  "name": "@jayjex/dataset-mcp",
  "version": "1.1.0",
  "type": "module",
  "bin": { "dataset-mcp": "index.js" },
  "files": ["index.js", "README.md"],
  "engines": { "node": ">=18" }
}

Three details do the work. The shebang (#!/usr/bin/env node) on the entry file's first line makes it executable when npx fetches it. The bin field names the command. The files field keeps the published payload to the entry file and README instead of the whole repo history.

One npm-version wrinkle: npm 12 refuses git-based installs by default, so the git form needs the flag first, and that is the form our own docs tell people to copy:

# npm 12+
npx --allow-git=all -y github:jayjex/dataset-mcp
# npm 10 and 11
npx -y github:jayjex/dataset-mcp

Without the flag, npm 12 exits with EALLOWGIT before your code runs. Setting allow-git=github.com once in ~/.npmrc removes the need for the flag everywhere. The full config-file walkthrough lives in the MCP server for Claude Desktop guide.

For discovery beyond people who already have your repo URL, add a server.json declaring your registry name; dataset-mcp is listed as io.github.jayjex/dataset-mcp in the official registry. The format mirrors the package: name, description, repository URL, version.

From 76 lines to a production server

The notes server and dataset-mcp share the same skeleton: a request loop, a method dispatcher, tools that return JSON text in a content block, tool-level errors that list valid inputs. What production adds is scope, and dataset-mcp's choices each solve one problem:

Keep data out of the server. dataset-mcp ships zero data files. A catalog.json and a release manifest describe the datasets, full CSVs download from a public GitHub release on first query into ~/.cache/dataset-mcp/, and every load re-verifies the file's SHA-256 against the manifest. The server stays a 25 KB single file; the data scales independently.

Push filtering into the tool schema. Five tools cover the whole surface (list_datasets, get_dataset_info, get_sample, query_dataset, get_stats) over 149,673 rows. query_dataset takes where clauses with =, contains, gt, lt, column picking, and next_offset paging at 100 rows per call, all declared in the tool's input schema so clients can build correct calls without reading source.

Measure and print the timing. Warm queries against cached files run 180 to 400 ms; a cold first call adds a one-time download, about 1.5 s including parse for the 3.6 MB NYC file. Publishing those numbers sets expectations and makes regressions visible.

A second production server, pdfcheck-mcp, runs the same skeleton over a different job: it walks PDF page-tree graphs (Kids to Page, Contents to stream, orphans, Count) and ships on npm as @jayjex/pdfcheck-mcp. The QA logic behind it, walked in Python against a healthy and a broken-wiring fixture, is the PDF page-tree QA guide.

The tool-level API is documented in depth on the dataset-mcp server page, and the MCP tools list indexes all three servers we run if you want more examples of tool sets before designing your own. The protocol details behind all of this are in the official docs at modelcontextprotocol.io.

FAQ

How much code does a minimal MCP server need?

The server on this page is 76 lines of Python with no dependencies beyond the standard library, and it answers initialize, tools/list, and tools/call. A working server needs those three methods plus one JSON response per line on stdout. Handing schema validation and the rest of the spec to the official SDK costs about 40 lines of JavaScript for a comparable tool set.

Do you need the MCP SDK to build an MCP server?

No. The Model Context Protocol is JSON-RPC 2.0 over a transport, and stdio servers are the simplest case: read a JSON object per line, write one back. The raw server on this page passed a handshake, a tools/list, and two tools/call requests from a client built on the official TypeScript SDK 1.30.0. The SDK still earns its keep beyond the basics: input validation against the schemas, request batching, and the other transports.

How do I publish an MCP server so clients can install it with npx?

Put the entry file at the repo root with a shebang line, point the bin field of package.json at it, and list it in the files field so the published package stays small. Clients can then run it with npx github:youruser/your-repo. On npm 12 the git-based form needs --allow-git=all first, which is how dataset-mcp ships: npx --allow-git=all -y github:jayjex/dataset-mcp. For registry listings, add a server.json declaring a name like io.github.jayjex/dataset-mcp.
