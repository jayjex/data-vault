Python read CSV: a pandas read_csv tutorial with real output

Published 2026-09-10. Every output block on this page is what the command actually printed on 2026-09-10, pandas 3.0.5 on Python 3.12, against files you can download from this site.

pd.read_csv loads any well-formed CSV in one line, and on the way it makes a decision about every column: what type it is. The decision is a guess from the first rows, and when the guess is wrong it usually fails silently. A ZIP code loses its leading zero and every join on it misses. A header row you meant to name becomes data row zero. A date column stays a string. This page runs the parameters that control those decisions against real CSVs from this site, with the verbatim output of each run, and shows what a wrong default costs.

What the default does

Start with the default call against the 22-row sample of the HUD Fair Market Rents FY2026 file:

import pandas as pd

df = pd.read_csv("sample.csv")
print(df.shape)
print(df.dtypes)
(22, 10)
zip              int64
hud_area_code      str
metro              str
area_name          str
state              str
fmr_0br          int64
fmr_1br          int64
fmr_2br          int64
fmr_3br          int64
fmr_4br          int64
dtype: object

No download step needed; the same sample loads straight from its URL, which FMR dataset download shows. The five fmr columns inferred int64 correctly and need nothing. The column to argue with is zip.

dtype: the bug pandas never warns about

Run the same default load against the full file, fmr-by-zip-2026.csv, 51,895 rows, and look at the smallest ZIP in it:

import pandas as pd

df = pd.read_csv("fmr-by-zip-2026.csv")
print(df["zip"].dtype)
print(df["zip"].min())
print(df.loc[df["zip"] == 601, "area_name"].iloc[0])
int64
601
Puerto Rico HUD Nonmetro Area

The ZIP is 00601 in the file. pandas turned it into the integer 601, and the same happened to every ZIP in the 006xx Puerto Rico range and the 0xxxx New England range. Count them:

print((df["zip"] < 10000).sum())
3533

3,533 of 51,895 rows silently corrupted. No exception, no warning column in the dataframe. The values still sort and group, so plots and medians look fine; the break only appears when you join against a geography table that has "00601" and find nothing. The fix is one argument:

df = pd.read_csv("fmr-by-zip-2026.csv", dtype={"zip": "string"})
print(df["zip"].min())
print(df.dtypes.iloc[0])
00601
string

Every leading zero survives. Any column of codes, not quantities, deserves this: ZIPs, FIPS codes, phone numbers, invoice IDs. If the file went the other direction, wrong bytes instead of wrong types, that is the domain of CSV encoding and UTF-8, which reproduces the mojibake and BOM traps the same way. And once the dataframe is correct, CSV to JSON in Python covers converting it without losing the types you just set.

usecols: load less, keep memory

Most analysis touches a few columns. Load only those:

df = pd.read_csv("sample.csv", usecols=["zip", "area_name", "fmr_2br"])
print(df.shape)
print(df.head(3))
(22, 3)
     zip        area_name  fmr_2br
0  76437  Abilene, TX MSA     1090
1  76443  Abilene, TX MSA     1090
2  76464  Abilene, TX MSA     1090

On the sample the saving is trivial. On the full file it is measurable in bytes:

full = pd.read_csv("fmr-by-zip-2026.csv")
small = pd.read_csv("fmr-by-zip-2026.csv", usecols=["zip", "fmr_2br"])
print(full.memory_usage(deep=True).sum())
print(small.memory_usage(deep=True).sum())
15317674
830452

15.3 MB down to 0.83 MB, an 18x cut, from naming two columns. usecols also accepts callables (usecols=lambda c: c.startswith("fmr")) when you want all fmr sizes without listing them. One honest caveat: pandas still parses the whole file to reach the last column; usecols saves memory, not read time.

parse_dates: stop parsing dates by hand

Date columns load as text by default. The 22-row sample of the NFL games dataset carries a gameday column in ISO format, which makes the change easy to see:

import pandas as pd

df = pd.read_csv("nfl-games.csv")
print(df["gameday"].dtype)
df = pd.read_csv("nfl-games.csv", parse_dates=["gameday"])
print(df["gameday"].dtype)
print(df["gameday"].min().date(), df["gameday"].max().date())
str
datetime64[us]
1999-09-12 1999-09-19

Without parse_dates, the column is str, and the first date arithmetic you try fails loudly: df["gameday"].dt.year raises AttributeError. With it, real datetime operations work immediately:

print(df["gameday"].dt.year.unique().tolist())
[1999]

Unlike the ZIP bug, this one announces itself. That is the split worth keeping in mind across the whole parameter list: dtype mistakes are silent, parse_dates omissions are loud. Loud costs minutes; silent ships wrong numbers.

na_values: what counts as missing

Empty cells become NaN by default, along with "NA", "N/A", "null", and a short list more. In the NFL sample every 1999 game has an empty gametime cell, and six rows have no temp:

df = pd.read_csv("nfl-games.csv")
print(df["gametime"].isna().sum())
print(df["temp"].isna().sum())
22
6

Sometimes you want raw control, for example when a legitimate value in your data collides with the default list. keep_default_na=False turns all of it off, and then empty cells stay empty strings:

df = pd.read_csv("nfl-games.csv", keep_default_na=False)
print(df["gametime"].dtype)
print(repr(df.loc[3, "gametime"]))
str
''

Build your own missing-value list with na_values on top:

df = pd.read_csv("nfl-games.csv", keep_default_na=False, na_values=[""])
print(df["gametime"].isna().sum())
print(df["temp"].isna().sum())
22
6

Now exactly one string counts as missing, the empty cell, and a literal "NA" in some other column would survive as text instead of vanishing into NaN. The silent version of getting this wrong: a column of country codes containing "NA" for Namibia, which the default list converts to NaN, and half your Caribbean analysis disappears without an error.

chunksize: process a file in pieces

Hand chunksize to read_csv and it returns an iterator instead of a dataframe. Each pass gives you the next N rows. Run the full HUD file in 10,000-row chunks and track a running maximum:

import pandas as pd

rows = 0
high = 0
for i, chunk in enumerate(pd.read_csv("fmr-by-zip-2026.csv", chunksize=10000)):
    rows += len(chunk)
    high = max(high, chunk["fmr_2br"].max())
    print(f"chunk {i}: {len(chunk)} rows, running max fmr_2br {high}")
print(rows, "rows total, max fmr_2br", high)
chunk 0: 10000 rows, running max fmr_2br 4410
chunk 1: 10000 rows, running max fmr_2br 4760
chunk 2: 10000 rows, running max fmr_2br 5230
chunk 3: 10000 rows, running max fmr_2br 5230
chunk 4: 10000 rows, running max fmr_2br 5230
chunk 5: 1895 rows, running max fmr_2br 5230
51895 rows total, max fmr_2br 5230

Six chunks, 51,895 rows counted, and the highest 2BR FMR in the file found without ever holding more than 10,000 rows. Only one thing changes when you go chunked: each chunk carries its own dtypes and its own NaN inference, so a column that looks numeric in early chunks can land as text in a later one. Pass explicit dtype values when you iterate, and the pieces behave like one load. The pattern for anything bigger than RAM: chunksize to iterate, usecols to shrink each piece, dtype to keep them consistent.

sep: when the separator is wrong

Semicolon exports from European Excel, tab files, pipe-delimited dumps: sep takes any of them (sep=";", sep="\t", or its alias delimiter). What a wrong separator does is quiet:

df = pd.read_csv("sample.csv", sep="|")
print(df.shape)
print(df.columns[0])
(22, 1)
zip,hud_area_code,metro,area_name,state,fmr_0br,fmr_1br,fmr_2br,fmr_3br,fmr_4br

22 rows, one column, and the whole header line as the column name. No error. The giveaway comes later, in df.columns or the first KeyError on a column that obviously exists. If you do not know the file, let pandas sniff it:

df = pd.read_csv("sample.csv", sep=None, engine="python")
print(df.shape)
print(df.columns.tolist()[:3])
(22, 10)
['zip', 'hud_area_code', 'metro']

sep=None requires the slower Python engine and inspects the first rows for the delimiter. It detected the comma and returned the full 10 columns. Use it once to learn the answer, then hardcode the real separator for speed.

header and names: who owns row zero

The last pair controls the top of the file, and its failure mode is a favorite of data pipelines: row counts that are off by one forever. Pass custom names to a file that already has a header, and pandas keeps the header row as data:

cols = ["zip", "hud_area_code", "metro", "area_name", "state",
        "fmr_0br", "fmr_1br", "fmr_2br", "fmr_3br", "fmr_4br"]
df = pd.read_csv("sample.csv", names=cols)
print(len(df))
print(df.iloc[0].tolist())
23
['zip', 'hud_area_code', 'metro', 'area_name', 'state', 'fmr_0br', 'fmr_1br', 'fmr_2br', 'fmr_3br', 'fmr_4br']

23 rows, and row zero is the header line itself wearing your new column names. Everything downstream inherits the off-by-one. Add header=0 to say the first line is a header to replace, and the count lands where it should:

df = pd.read_csv("sample.csv", names=cols, header=0)
print(len(df))
print(df.iloc[0].tolist())
22
[np.int64(76437), 'METRO10180M10180', 'metro', 'Abilene, TX MSA', 'TX', np.int64(850), np.int64(880), np.int64(1090), np.int64(1420), np.int64(1710)]

The mirror case: a genuinely headerless file read with the default silently loses its first data row to become the column names. Force header=None when there is no header, and pandas numbers the columns 0 through 9:

df = pd.read_csv("sample.csv", header=None)
print(df.shape)
print(df.iloc[0].tolist()[:3])
(23, 10)
['zip', 'hud_area_code', 'metro']

The rule in one line: header=0 with names replaces an existing header; header=None declares there is none; anything else costs you one row and usually a week.

The parameters at a glance

ParameterDoesWhen it matters
dtypeForces a column's typeCodes and IDs. Silent corruption: 00601 becomes 601, no warning.
usecolsLoads named columns onlyMemory: 15.3 MB to 0.83 MB on the full FMR file. Parse cost unchanged.
parse_datesParses date columns to datetime64Loud failure if omitted: .dt raises AttributeError on str.
na_valuesExtends the missing-value listSentinel text. Silent: "NA" country codes become NaN by default.
chunksizeReturns an N-row iteratorFiles bigger than RAM. Pass dtype explicitly, chunks infer separately.
sepSets the field separatorWrong separator = one column, no error. sep=None sniffs once.
header, namesControl the first rowOff-by-one row counts, header as data. Silent for weeks.

Sort the table by failure mode and the pattern is blunt: the parameters that fail loudly waste minutes, the ones that fail silently poison the data. dtype, sep, and header belong in every load call for files you did not generate yourself; usecols, parse_dates, na_values, and chunksize come in as the file and analysis grow.

Python read CSV FAQ

How do I read a CSV file in Python?

With pandas, one line: import pandas as pd, then df = pd.read_csv("file.csv"). pandas infers the column types, so integers load as int64 and everything else as text. One inference to override on any file with postal or area codes: pass dtype={'zip': 'string'} so leading zeros survive. For file objects you want as lists and dicts instead of a dataframe, the csv module from the standard library does the same read; CSV to JSON in Python shows both converters on real output.

Why does pandas turn my ZIP code into a number?

read_csv looks at the first rows, sees only digits in the zip column, and assigns int64. A ZIP like 00601 becomes the integer 601, and the zero is gone. In the 51,895-row FY2026 fair market rent file, 3,533 rows have ZIPs starting with 0, and none of them raises an error or a warning. Fix it at load time with dtype={'zip': 'string'}, which keeps the value as the text '00601'.

How do I read a large CSV file in pandas without running out of memory?

Two parameters do the work. chunksize=N makes read_csv return an iterator of N-row dataframes, so you aggregate chunk by chunk and never hold the whole file: the same 51,895-row file that takes 15.3 MB in memory processes in 10,000-row pieces. usecols cuts what you keep: loading only zip and fmr_2br from that file takes 0.83 MB instead of 15.3 MB. Combine both for files bigger than RAM.
