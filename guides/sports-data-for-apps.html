Sports data for apps: free APIs tested live, licenses, and the cache architecture

App-developer view of free sports data sources · companion to the NFL data APIs comparison and the free sports data CSV survey · every status code and output comment below comes from a live run on 2026-09-10.

Three free sources cover most of what a sports app needs, and they behave very differently in production:

SourceWhat it gives the appChecked 2026-09-10License standing
ESPN site APILive scores, fixtures, teams, every major leaguenfl/scoreboard 200, 16 events · nba 200, mlb 200, nhl 200undocumented, no reuse guarantee

The short version: ESPN for the live layer, nflverse for the history layer, TheSportsDB when you need leagues ESPN's feed makes awkward or a second opinion on fixtures. None of them should be called from your app process directly; the architecture section shows where they belong instead.

ESPN site API: the live layer

ESPN serves the JSON its own site and apps render, under site.api.espn.com, keyless. The scoreboard endpoint worked for all four major leagues on the checked date:

import requests

r = requests.get(
    "https://site.api.espn.com/apis/site/v2/sports/football/nfl/scoreboard",
    timeout=30,
)
r.raise_for_status()
print(r.status_code, len(r.content))    # 200 200379
print(len(r.json()["events"]))          # 16
print(r.json()["events"][0]["name"])    # New England Patriots at Seattle Seahawks

for sport, league in [("basketball","nba"), ("baseball","mlb"), ("hockey","nhl")]:
    r = requests.get(f"https://site.api.espn.com/apis/site/v2/sports/{sport}/{league}/scoreboard", timeout=30)
    print(sport, r.status_code, len(r.json().get("events", [])))
    # basketball 200 1 | baseball 200 15 | hockey 200 7

The teams endpoint returned all 32 NFL clubs the same day (200, 148,848 bytes). What an app gets: nested JSON with event status, odds when posted, venue, and broadcast info, one call per league per day window.

The catch is the contract. This is an undocumented site API: no published schema, no versioning promise, no published rate limit, and no reuse terms for commercial apps. It has been stable for years and every hobby project leans on it, but your launcher or store review is not the place to discover a breaking change. Cache responses (the architecture below does), pin your parser to the fields you actually use, and keep timeouts on. For endpoint-by-endpoint examples, the ESPN API in Python guide.

nflverse releases: the history layer

The nflverse-data project publishes complete NFL game data as static GitHub release files. This is the cleanest license in the space: CC BY 4.0, commercial use allowed with credit as "Data from nflverse, CC BY 4.0". A single file carries every game since 1999:

url = "https://github.com/nflverse/nflverse-data/releases/download/schedules/games.csv"
r = requests.get(url, timeout=120)
r.raise_for_status()
print(r.status_code, len(r.content))    # 200 2178569
print(r.content.count(b"\n"))           # 7549  (7548 rows + header)
print(r.content.split(b"\n")[0][:46])   # game_id,season,game_type,week,gameday,weekday,

stamp = requests.get(
    "https://github.com/nflverse/nflverse-data/releases/download/schedules/timestamp.json",
    timeout=30,
).json()
print(stamp)    # {'last_updated': '2026-09-07 09:51:20 EDT'}

For an app, the pattern is a sync job, not a query: download the file, diff it against your cache, load the new rows. The timestamp.json stamp tells the sync whether anything changed, so a daily download that sees the same stamp costs you nothing. Releases include schedules, play-by-play, rosters, and weekly player stats, each with its own stamp. Usage terms per source sit in the licensing section below; the full column-by-column breakdown is in the games.csv column guide.

TheSportsDB free tier: wide coverage, hard caps

TheSportsDB is a community-built database of teams, players, events, and artwork across dozens of sports. The free tier uses the public key 123 right in the URL, documented on the site's API page along with the limit: 30 requests per minute, enforced with a 429 and a one-minute cooldown. Tests on the checked date, verbatim:

K = "123"
base = f"https://www.thesportsdb.com/api/v1/json/{K}"

r = requests.get(f"{base}/searchteams.php?t=Arsenal", timeout=30)
print(r.status_code, len(r.content))          # 200 17209
print(r.json()["teams"][0]["idTeam"])         # 133604

r2 = requests.get(f"{base}/eventsnextleague.php?id=4328", timeout=30)
evs = r2.json()["events"]
print(r2.status_code, len(r2.content), len(evs))   # 200 1684 1
print(evs[0]["strEvent"])                          # Bournemouth vs Brentford

r3 = requests.get(f"{base}/eventsday.php?d=2026-09-10&s=Ice%20Hockey", timeout=30)
print(r3.status_code, len(r3.json()["events"]))   # 200 3
print(r3.json()["events"][0]["strEvent"])         # Sibir Novosibirsk vs Amur Khabarovsk

The free tier trims results, and the trims are visible in the responses above. eventsnextleague.php for the English Premier League returned 1 upcoming event; premium keys return the full next-5 list. eventsseason.php?id=4328&s=2025-2026 answered 200 but with 5 events where the real season has 380. search_all_teams.php?l=NFL returned 10 of 32 clubs. The livescore methods answer [null] on the free key (latestsoccer.php returned exactly that), and the v2 API rejects non-premium keys outright (404 on a plain test). None of that makes the free tier useless: team lookups, venue data, artwork, and day-level event listings all work, and 30 req/min is enough for a poller that syncs once or twice a minute.

Licensing sits in the site's database terms: the data is community-contributed, the free tier is for development and light use, and heavy or commercial use is what the premium tier funds. Read their current terms before shipping; they are stricter than a CC license.

Typical app architecture: poll, cache, serve

The mistake every first sports app makes is calling source APIs from the request path. One user spike burns the rate limit, and when ESPN's endpoint hiccups, your app is down with it. The standard fix is three processes with one boundary between them:

  source APIs            poll worker              cache            app API
 (ESPN, nflverse,  ──▶  (cron / scheduler)  ──▶  (SQLite /   ◀──  (serves users;
  TheSportsDB)          poll per freshness        Postgres)        never calls sources)
                        target per table          normalized
                                                  rows + TTL

Or as one rule: the app API only ever reads your cache. The poller is the single client of the outside world. Concretely:

  • Poll worker. One scheduled job per table, cadence set by how fast the data actually changes (table below). It calls the source, maps the response into your own schema, and writes. Normalization lives here, so ESPN's nested competitions[0].competitors never leaks past this box.
  • Cache. Any database you like. Two things matter: rows in your schema, not the source's, and a TTL or updated_at per table so the app knows how fresh each read is. This is also your outage shield: if ESPN goes down at kickoff, the cache still serves the last good poll.
  • App API. Reads the cache, answers users, scales horizontally without touching a rate limit. Version your own API; the sources behind it can change without a user-visible release.

Rate limit strategy, per source

The poller makes rate limits a solved problem, but the numbers still decide your cadence:

SourcePublished limitWhat it means for the poller
ESPN site APInone publishedact like there is one: keep total calls modest, cache everything, back off on 5xx. A 16-game NFL Sunday polled every 60s is about 180 calls across a 3-hour window, trivially safe
TheSportsDB free tier30 req/min, 429 then one-minute cooldown (documented)budget ~25/min to leave headroom; on 429, sleep 60s. One league's daily sync is a handful of calls, so the limit binds only if you fan out across dozens of leagues
nflverse releasesnone (GitHub asset downloads)stamp check first, download only on change; a daily sync is 1-2 requests

Three habits cover the rest. Back off with jitter on any 429 or 5xx rather than retrying on a fixed interval, or your poller becomes the outage. Log the byte size of each response; a sudden change usually means a schema change landed. And record each poll's stamp or ETag so unchanged days cost nothing.

Sports data for apps: FAQ

What is the best free sports data API for an app?
Match the source to what the app shows. ESPN's site API for current scores and fixtures, keyless and tested at 200 across NFL, NBA, MLB, and NHL on 2026-09-10. nflverse for complete NFL game history as CSV under CC BY 4.0, 7,548 games from 1999. TheSportsDB's free tier for multi-league team and event lookups at 30 requests per minute. Many apps combine all three: ESPN for the live layer, nflverse for history, TheSportsDB for coverage ESPN does not carry.
Can I use ESPN's API in a commercial app?
There is no contract that says you can. The site.api.espn.com endpoints are undocumented, carry no published terms for programmatic reuse, no schema guarantee, and no published rate limit. Apps do use them and the endpoints answer any client, but the content is ESPN's and the endpoints can change or close without notice. Keep your own cache so an outage degrades your app gracefully instead of breaking it, and treat a commercial launch as the point to evaluate a licensed feed.
How do I avoid rate limit problems in a sports app?
Never call the source APIs from your app process. Run one poller that fetches on a schedule, writes normalized rows into your own cache, and serve users from the cache. Set a freshness target per table: scores need 30 to 60 second polls during game windows, schedules change once a day, historical records never change. Honor 429 responses by waiting, as TheSportsDB documents for its 30 requests per minute free tier, and back off with jitter on any 5xx.
