Drinking water points in Tokyo, Jakarta and Seoul, counted from OpenStreetMap

Published 2026-09-10. Data source: OpenStreetMap Civic Amenities, Tokyo-Jakarta-Seoul, 2026-09, nine node counts from Overpass API out count queries on 2026-09-10, kumi mirror base timestamp 2026-07-24. Boundary details come from the dataset schema. This page documents the data.

The short answer

Three capitals, three amenity types, nine counts, and one capital holding nearly everything. OpenStreetMap contributors have mapped 2,489 public features inside the boundaries of Tokyo, Jakarta, and Seoul: 2,454 drinking water points, 4 public bookcases, and 31 bike repair stations, a node snapshot taken 2026-09-10 on a database whose documented base timestamp is 2026-07-24. Tokyo holds 2,191 of the features, 88.0 percent of the file, and its drinking-water count alone (2,163) covers 88.1 percent of the fountains in all three cities combined.

The file's one zero cell and its unnamed rows say as much about mapping culture as the thousands do. Jakarta has no mapped public bookcase, and two of its three rows carry no name tag at all. Both tables below recompute from the free nine-row CSV, and the two SQL blocks at the end of this page return them verbatim.

Three capitals, three writing scripts

Unlike the count-only US, EU, and Africa files, each Asia row carries an example node: its name tag verbatim, with latitude and longitude. The names come back in three scripts. Tokyo's bookcase example is named 音楽ライブラリー (a music library shelf) at 35.68241, 139.71942, and its repair-station example is 自転車修理いむら商会 (Imura Shokai, a bike shop) at 35.72883, 139.68391. Seoul's drinking-water example is named 아리수 (Arisu) at 37.55575, 126.89504, and its repair-station example is 서울자전거 at 37.51372, 127.10091. Jakarta's drinking-water example reads galon c2 at -6.09890, 106.96190.

Two of Jakarta's three rows carry an empty name tag, and Tokyo's drinking-water example carries the generic tag name fountain at 35.56829, 139.45574. The file records what the tags say, nothing more; what Arisu stands for, or who fills the galon c2 bottles, is context the CSV does not carry. For an agent or a pipeline, that column is a free sample of the map's texture; pull one row and you get a name and a coordinate you can plot.

One real zero and a placeholder coordinate

Zeros in a count table can mean two things: nobody mapped the thing, or nobody mapped the tag. The schema answers for Jakarta's bookcase cell: no public_bookcase is mapped yet inside the Jakarta relation boundary. Because the count is 0, no example node exists, and the row's coordinates (-6.20000, 106.81667) are a city-center placeholder, which the schema states outright. Every other cell in the file has a real node behind it.

The rest of the series puts the small bookcase base in context. Seattle holds the catalog peak at 497 in the 16-city US file, Paris 165, Berlin 114, and Warsaw 33 in the EU file; in Asia, Tokyo's 3 is the high mark and Seoul adds 1. The EU file's Amsterdam also reads 0 while Berlin in the same file reads 114, so a zero next to a busy column is a mapping-culture gap that shows up inside one region too. Whether Jakarta's 0 will stay 0 is a question the file cannot answer.

Where Tokyo stands across the series

Cross-file, Tokyo's 2,163 drinking-water points rank third among single-city counts in the catalog's eight-file civic series. Sydney holds the top count at 2,479 in the Oceania file, Nairobi follows at 2,174, and Tokyo leads Madrid (2,058) and New York (1,599 in the 16-city US file). Seoul's 253 lands one fountain above Chicago's 252 in the exact-boundary US2 file, and Jakarta's 38 sits second-lowest in the series, ahead of only Addis Ababa's 5.

The repair column earns an honest downgrade. Tokyo's 25 bike repair stations lead the Asia file and outnumber the entire MENA file's repair total (Istanbul 16, Cairo 0, Mumbai 3, together 19), but across the series 25 ranks ninth: Warsaw's 188 stands top the catalog, with Berlin (71), Paris (52), Los Angeles (44), Chicago (40), New York (31), Austin (28), and Seattle (28) all ahead. The comparison stays within a theme on purpose: the Oceania and US2 files count fountains, toilets, and benches, so a bench-to-fountain ratio does not transfer across files. What does transfer is the drinking-water column, which every file measures with the same amenity=drinking_water tag.

One counting rule differs from the Africa lane and matters for close comparisons: this file counts nodes only, and the schema notes that some amenities are mapped as ways, rare for these three tags. The Africa file counted nodes and ways together. A way mapped as a drinking fountain would appear in the Africa numbers and not here, which is one more reason to treat single-digit differences between regions as snapshot noise rather than rankings.

Methodology: nodes only, one documented base timestamp

The source file is the nine-row counts-2026-09.csv (ODbL, © OpenStreetMap contributors). Each cell is an Overpass API out count query for one amenity type inside one city area, counting nodes only; ways and relations are ignored, and the schema flags ways as rare for these three tags. City areas were resolved through Nominatim relations and passed to Overpass as 3600000000-offset area IDs: Tokyo Metropolis (R3601543125), Daerah Khusus Ibukota Jakarta (R6362934), and Seoul Special City (R2297418).

The counts ran on 2026-09-10 against the kumi.systems and maps.mail.ru Overpass mirrors, and the schema documents the kumi base timestamp as 2026-07-24, 48 days before the count date. Unlike the Africa file, this schema publishes no second-mirror drift table, so this page makes no mirror-agreement claim. Counts are a snapshot, OSM moves daily, and all three boundaries are metro-scale admin areas that reach past the downtown cores, so read the numbers as OpenStreetMap coverage inside these boundaries: exact for what was mapped, estimates for what stands on the ground.

Recompute the tables yourself

Load the CSV into SQLite as civic, seven columns per row. The first block returns the raw board:

-- SQLite: all nine city-amenity counts, ranked by raw count
CREATE TABLE civic (city TEXT, amenity TEXT, total INT, tags TEXT, lat TEXT, lon TEXT, source TEXT);
.import --skip 1 counts-2026-09.csv civic

SELECT rn, city, amenity, total, share_of_city
FROM (SELECT city, amenity, total,
             ROUND(total * 100.0 / SUM(total) OVER (PARTITION BY city), 1) AS share_of_city,
             ROW_NUMBER() OVER (ORDER BY total DESC, city, amenity) AS rn
      FROM civic)
ORDER BY rn;
-- Rows: 1 Tokyo drinking_water 2163 98.7,
-- 2 Seoul drinking_water 253 97.7,
-- 3 Jakarta drinking_water 38 97.4,
-- 4 Tokyo bicycle_repair_station 25 1.1,
-- 5 Seoul bicycle_repair_station 5 1.9,
-- 6 Tokyo public_bookcase 3 0.1,
-- 7 Jakarta bicycle_repair_station 1 2.6,
-- 8 Seoul public_bookcase 1 0.4,
-- 9 Jakarta public_bookcase 0 0.0.

The second block returns the file's shape: theme totals, Tokyo's share, the median, the zero-cell count, and the span across nonzero cells, then per-city totals:

-- SQLite: shape of the file
WITH r AS (SELECT total AS v, ROW_NUMBER() OVER (ORDER BY total) AS rn,
                  COUNT(*) OVER () AS n FROM civic),
     t AS (SELECT amenity, SUM(total) AS n FROM civic GROUP BY amenity),
     c2 AS (SELECT city, SUM(total) AS n FROM civic GROUP BY city)
SELECT
  (SELECT SUM(v) FROM r) AS features,
  (SELECT n FROM t WHERE amenity = 'drinking_water') AS drinking_water,
  (SELECT n FROM t WHERE amenity = 'public_bookcase') AS bookcases,
  (SELECT n FROM t WHERE amenity = 'bicycle_repair_station') AS repair_stations,
  (SELECT n FROM c2 WHERE city = 'Tokyo') AS tokyo_total,
  (SELECT ROUND(n * 100.0 / (SELECT SUM(n) FROM c2), 1) FROM c2
   WHERE city = 'Tokyo') AS tokyo_share,
  (SELECT v FROM r WHERE rn = (n+1)/2) AS median_count,
  (SELECT SUM(CASE WHEN v = 0 THEN 1 ELSE 0 END) FROM r) AS zero_cells,
  (SELECT MAX(v) FROM r) AS largest_count,
  (SELECT ROUND(MAX(v) * 1.0 / MIN(v), 1) FROM r WHERE v > 0) AS largest_over_floor;
-- 2489 / 2454 / 4 / 31 / 2191 / 88.0 / 5 / 1 / 2163 / 2163.0.

-- per-city totals and the drinking-water share
SELECT city, SUM(total) AS city_total,
       ROUND((SELECT total FROM civic WHERE city = c.city AND amenity = 'drinking_water')
             * 100.0 / SUM(total), 1) AS drinking_share
FROM civic c
GROUP BY city
ORDER BY city_total DESC;
-- Rows: Tokyo 2191 98.7,
-- Seoul 259 97.7,
-- Jakarta 39 97.4.

Run in one session, both blocks return exactly the rows quoted in the comments. The drinking-water share stays above 97 percent in every city because each city's file is, to one decimal, nearly all fountains.

Tokyo, Jakarta and Seoul counts: questions

Which of the three cities has the most drinking water points?
Tokyo on raw counts: 2,163 of the file's 2,454 drinking-water features, 88.1 percent of the theme, against Seoul's 253 and Jakarta's 38. Cross-file, Tokyo's 2,163 ranks third among single-city drinking-water counts in the catalog's eight-file civic series, behind Sydney (2,479) and Nairobi (2,174) and ahead of Madrid (2,058). All three Asian counts run inside admin-boundary relations, so the numbers cover the whole metropolis rather than the downtown core.
Why does Jakarta show zero public bookcases?
The schema states it as a real result: nobody has mapped a public_bookcase yet inside the Jakarta relation boundary, so the count is 0 and the row's coordinates are a city-center placeholder rather than a node location. The rest of the file backs the small base: Tokyo counts 3 public bookcases and Seoul 1, and no Asian city passes single digits. Across the catalog's civic series, Seattle holds the bookcase peak at 497, Paris 165, and Berlin 114, so the Asian numbers sit at the low end of a tag that never caught on in the region.
How were the counts taken and verified?
Each cell is an Overpass API out count query for one amenity type inside one verified boundary relation, run on 2026-09-10 against the kumi.systems and maps.mail.ru mirrors; the schema documents the kumi base timestamp as 2026-07-24, 48 days before the count date. Counts cover nodes only, and the schema notes some amenities are mapped as ways, which is rare for these three tags. On this page every number was recomputed with python and independently in SQLite, and the two SQL blocks return their quoted outputs verbatim.
