What is JSON-LD?

Published 2026-09-10. Every block below is copied from pages live on this site: all 170 HTML pages carry at least one JSON-LD block, most carry three.

The short answer

JSON-LD (JavaScript Object Notation for Linked Data) is a way to describe what a page is about in a machine-readable block, using vocabulary from schema.org. You write it as a JSON object inside one tag, <script type="application/ld+json">, in the page head. A crawler reading that block learns: this page is an article, published on this date, updated on that one, by this organization. These three questions appear on it. This URL belongs to this section of this site.

Google recommends JSON-LD over the two older structured data formats. The older ones, microdata and RDFa, wrap attributes around the visible HTML, so a sitewide change means editing markup everywhere. JSON-LD keeps the data in one block per page, apart from the content. That single design choice is why it became the practical default: one place to write, one place to maintain, and a format any JSON parser can read.

What JSON-LD does in search

Structured data does not raise rankings. It qualifies pages for rich results, the enhanced listings Google shows when markup matches a supported type. A page with valid FAQPage markup can show its questions as expandable entries under the search listing. A page with BreadcrumbList shows a section trail instead of a raw URL. An Article block feeds the headline, dates, and publisher into how Google understands and sometimes displays the page.

The second effect is quieter but bigger on large sites: disambiguation. A crawler that lands on a URL with no markup has to infer what the page is from title and text. The markup removes the inference. On a catalog like this one, where guide pages, dataset pages, and tool pages all live close together, the type declarations tell the crawler which page belongs to which category without guessing.

The four schema.org types that earn their keep

Hundreds of schema.org types exist. Four cover most of what a content site needs, and this page itself ships all four:

TypeWhat it declaresWhat it can do in search
ArticleHeadline, description, publish and modify dates, author, publisherHelps Google read the page as an article and keep dates fresh in listings
FAQPageA list of questions with their answers, matching visible page contentQualifies the page for FAQ rich results; Google requires the same Q&A to be visible on the page
BreadcrumbListThe page's position as an ordered chain from the site rootReplaces the raw URL in listings with a section trail
ItemListAn ordered list of things, each with a position and optional URLDescribes list pages and anchor tables so crawlers get the structure in one read

The FAQPage rule is the one people break most: the questions and answers in the markup must appear on the visible page. Markup that describes questions the page never shows fails eligibility, because Google treats the markup as a description of the page, not extra content.

How this site uses it: real blocks

All 170 HTML pages on this site carry JSON-LD, and every guide ships the same three blocks: Article, BreadcrumbList, and FAQPage. Here is what that looks like in practice.

Our HUD FMR by state guide has a 52-row table of per-state rent medians, one row per state, each row an anchor. The ItemList block mirrors that table with one ListItem per state. The real block, abridged:

{"@context": "https://schema.org", "@type": "ItemList",
 "name": "HUD FMR by state, FY2026 2BR medians", "numberOfItems": 52,
 "itemListElement": [
   {"@type": "ListItem", "position": 1, "name": "California (CA)",
    "url": "https://jayjex.github.io/data-vault/guides/hud-fmr-by-state.html#CA"},
   {"@type": "ListItem", "position": 2, "name": "Hawaii (HI)",
    "url": "https://jayjex.github.io/data-vault/guides/hud-fmr-by-state.html#HI"},
   ...]}

Fifty-two rows of markup is boring to write and worth the boredom: a crawler gets the full state-to-anchor map without parsing a table.

The FAQPage pattern is a mirror rule. We write the visible FAQ first, then copy the exact question and answer text into the JSON-LD block. The llms.txt guide shows the result: the markup's answer text and the page's visible answer text are identical, because one was copied from the other. One source of truth means the markup never claims content the page does not show, which is the failure mode that kills FAQ eligibility.

Every page also carries the BreadcrumbList block, two items deep here: Data Vault, then the page. This page is no exception. And the Article block on each guide carries dateModified, which we bump whenever a page changes, so listings keep showing a current date.

How to validate

Two tools cover it. Google's Rich Results Test takes a URL or pasted code and reports every rich result type the page qualifies for, with errors and warnings per block. The Schema Markup Validator checks the vocabulary itself, which matters for types Google has no rich result for: an ItemList of state anchors earns no rich result but can still be wrong.

The loop we run on every page here: paste the deployed URL into the Rich Results Test, confirm all three blocks are detected, fix any errors, re-test. The errors we have actually hit are mundane. A date in the wrong format instead of YYYY-MM-DD. A missing mainEntityOfPage. One trailing comma, which is invalid JSON and kills the entire block rather than the one item it sits on. None need a debugging session; all show up in the validator if you run it before shipping.

Worth one extra check after deploy: fetch the live page and confirm the script tags are in the served HTML, since a template change can drop a block without breaking anything visible.

FAQ

What is JSON-LD in simple terms?
JSON-LD is a block of JSON that describes what a page is about in machine-readable form, using the schema.org vocabulary. It sits in one script tag in the page head, separate from the visible HTML, and crawlers read it to identify the page type, publish dates, author, questions the page answers, and the page's position in the site structure.
Does JSON-LD help SEO?
Structured data does not directly change rankings. Its value is eligibility: pages with valid markup can appear as rich results, so a FAQPage can show expandable questions under the listing and a BreadcrumbList can replace the raw URL with a section trail. It also removes ambiguity for crawlers, which matters on large sites with thousands of pages. Treat it as a cheap qualification step, not a ranking lever.
How do I validate my JSON-LD?
Run the page through Google's Rich Results Test at search.google.com/test/rich-results. It lists every rich result type the markup qualifies for and flags errors per block. For vocabulary checks beyond Google's supported types, use validator.schema.org. Both tools accept a live URL or pasted code, so you can validate before deploying.
