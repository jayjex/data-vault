x402 API: how HTTP 402 pay-per-call works, with a live challenge

The monetized end of the public data APIs list · the demo API serves NFL game rows compared in the NFL data APIs guide · every status code, header, and JSON object on this page comes from live calls on 2026-09-10.

What the x402 API flow is

x402 is an open protocol for pay-per-call APIs. A server that charges per request answers an unpaid call with HTTP 402 and a machine-readable payment challenge in the PAYMENT-REQUIRED header. The client signs a USDC transfer on Base, resends the request with the signature attached, and a facilitator service verifies and settles the payment before the server returns data. No account, no API key, no invoice. The status code that sat reserved for three decades finally has a job.

We run a small two-endpoint data API on this stack: GET /nfl/scores (7,548 NFL games with betting lines from the nflverse releases, CC BY 4.0) and GET /hud/fmr (Fair Market Rents for 51,895 ZIPs, US HUD public domain). Every response quoted below is verbatim from live calls on 2026-09-10, and you can reproduce the first one with a single curl.

HTTP 402: reserved for thirty years, used now

402 Payment Required has been in the HTTP status list since the early specs, marked reserved for future use. No browser or framework ever shipped a payment flow for it, so APIs that charge did the gating out of band: sign-up walls, keys, monthly invoices, humans reading pricing pages. x402 keeps the status code and defines the machine-readable contract that travels with it, so the negotiation happens inside ordinary HTTP instead of a sales call. This page uses the v2 shape of the spec, documented at docs.x402.org.

The flow in three steps

  1. Challenge. An unpaid GET returns 402 with a PAYMENT-REQUIRED header (base64 JSON) and a readable JSON body. The challenge states what the server wants: asset, network, amount, destination wallet.
  2. Payment. The client picks one of the accepts entries, signs an EIP-3009 USDC transfer authorization for that amount (10,000 atomic units, which is 0.01 USDC at USDC's 6 decimals), and resends the request with a PAYMENT-SIGNATURE header.
  3. Verify and settle. The server POSTs the payload to the facilitator's /verify endpoint, which checks signature, amount, and asset. On a pass the server returns the data with a PAYMENT-RESPONSE header and the facilitator settles the transfer on-chain (Base mainnet, chain eip155:8453).

The PAYMENT-REQUIRED header carries the same object base64-encoded, so a client that reads only headers gets everything. The accepts entry is the part a buyer acts on:

One caveat about the hostname: the demo runs behind a Cloudflare quick tunnel, which rotates its URL when the service restarts. Treat the hostname as ephemeral and the response shape as the durable part. Two replay notes as of 2026-09-10: a fresh hostname may 404, and the two routes are now priced separately (NFL scores 10,000 atomic units, HUD FMR 1,000 atomic units per call), so a fresh challenge for /hud/fmr will show amount 1000 where the quote above shows 10000.

The same server also answers two free routes, GET /health and GET /catalog, with no payment header at all. The catalog doubles as machine-readable documentation of both paid routes.

Step 2: how a buyer calls a pay-per-call API

The buyer side is a few lines with the x402 SDK. This is the exact snippet from the demo API's README as of 2026-09-10. One correction worth knowing: .register() takes a scheme instance, not a raw signer, so the viem account goes inside ExactEvmScheme — the raw-signer form fails at request time:

import { x402Client, wrapFetchWithPayment } from "@x402/fetch";
import { ExactEvmScheme } from "@x402/evm/exact/client";
import { privateKeyToAccount } from "viem/accounts";

const client = new x402Client().register("eip155:8453",
  new ExactEvmScheme(privateKeyToAccount(process.env.EVM_PRIVATE_KEY)));
const paid = wrapFetchWithPayment(fetch, client);
const res = await paid("https://<PUBLIC_URL>/nfl/scores?season=2025"); // auto 402 -> sign -> retry

We smoke-tested this from a fresh npm install: plain fetch gets the readable 402 challenge, the wrapped client signs with a throwaway key and retries, and the facilitator returns a structured invalid_exact_evm_signature rejection (anvil dev key, no USDC). That is the full path minus the last paid step, and it is the same flow worked through with curl in the x402 endpoints gist.

What happens inside that wrapped call: the first request goes out unpaid, the 402 comes back, the client decodes PAYMENT-REQUIRED, matches it against the registered network signer, produces the EIP-3009 signature, and retries once with PAYMENT-SIGNATURE set. From the caller's perspective it reads like plain fetch. A client that skips the SDK does the same steps by hand: decode the header, sign the transfer authorization, resend. The extensions.bazaar block in the challenge goes further and advertises the input schema and an output example, so an agent can figure out what it is buying without reading a docs page.

The NFL route in that snippet serves scores and betting lines 1999-2026 from the nflverse releases; the sources behind those rows (ESPN, nflverse, the league's own closed API) are compared in the NFL data APIs guide.

Step 3: verify and settle, stated honestly

On the server side, a paid request is: decode PAYMENT-SIGNATURE, POST the payload to the facilitator's /verify, and serve data only on a pass, with PAYMENT-RESPONSE attached. The facilitator then settles the USDC transfer on-chain. Settlement rides on the facilitator (the demo uses facilitator.payai.network), which is the piece that turns a signed authorization into an actual Base transaction.

What we verified live on 2026-09-10, no hand-waving:

  • The 402 challenge fired on both paid routes through the public tunnel, with the header decoding to the v2 PaymentRequired shape shown above.
  • A malformed or v1-shaped header got a clean structured 402 back, server-side, no crash.
  • A verify roundtrip with a schema-valid payload carrying a fake signature reached the facilitator and returned its structured rejection (payment verification failed: invalid_payload), which proves the challenge shape is accepted end-to-end.
  • Settlement with a real signature is code-complete and tested up to the facilitator's response; no funded wallet sits on the box, so the final on-chain leg stays untested until the first payer arrives.

That last bullet is the honest state of the demo: everything a buyer touches is live, and the seller-side money leg is one funded signature away from proven.

Pay-per-call vs subscription for small data

Subscriptions price certainty; per-call prices use. At the demo's example rate of $0.01 per call, the math looks like this:

Monthly cost at $0.01 per call
Calls per monthCost at $0.01 per callWho fits
10ten centsone-off scripts, a weekend test
100one dollara cron job, a dashboard refresh
1,000ten dollarsan agent polling a few times an hour
10,000one hundred dollarssteady production traffic

Flat data tiers commonly start in the tens of dollars a month and charge the same whether you make 5 calls or 5,000. Around 2,500 calls a month at this example rate you reach the door of a 25-dollar tier, and steady volume above that is where a subscription's predictable billing starts to win. Below that, per-call has three practical edges for small data: no idle cost when traffic is spiky, no signup or key provisioning between deciding to call and calling, and one request carries its own payment so any HTTP client with a wallet can buy a single row set from a CI job or an agent at 3 a.m. without a human in the loop. High, steady, budget-capped usage still belongs on a flat plan.

FAQ

What is the x402 protocol?
An open spec for pay-per-call APIs. A server that wants money for a request answers with HTTP 402 and a machine-readable challenge in the PAYMENT-REQUIRED header; the client signs a USDC transfer on Base (an EIP-3009 authorization), resends the request with a PAYMENT-SIGNATURE header, and a facilitator service verifies and settles the payment so the server can return data. No account or API key is involved. The two-endpoint demo behind this page runs it live; the 402 response quoted below is verbatim from 2026-09-10.
How does an HTTP 402 payment work in practice?
Three steps. First the challenge: an unpaid GET returns 402 with a base64 PaymentRequired object that lists scheme exact, network eip155:8453 (Base mainnet), an amount in atomic units (10000 equals 0.01 USDC), the asset contract, and the payTo wallet. Second the payment: the client signs that USDC transfer and resends with PAYMENT-SIGNATURE. Third verify and settle: the server checks the payload through a facilitator, returns the data with a PAYMENT-RESPONSE header, and the facilitator settles the transfer on-chain.
When is pay-per-call cheaper than a subscription?
When usage is bursty or small. At the demo rate of $0.01 per call, 100 calls a month cost one dollar and 1,000 calls cost ten dollars, well under most flat data tiers; around 2,500 calls a month you reach the door of a 25-dollar tier, and steady volume above that favors a flat subscription with predictable billing. Agents, CI jobs, and MVPs with spiky traffic fit per-call; high steady volume with a fixed budget fits a subscription.
